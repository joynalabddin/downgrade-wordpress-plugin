# DevJoynal Downgrade — Latest GitHub Bug Audit

**Audit date:** 27 August 2026  
**Repository:** https://github.com/joynalabddin/downgrade-wordpress-plugin  
**Audited commit:** `f009b5f5610a84659a5f96eb4d911c3eb718d93c` (`Rename plugin to DevJoynal Downgrade`)  
**Release:** `v2.0.3`  
**Scope:** Functional behavior, Settings API, security boundaries, WordPress 7.1 compatibility assumptions, release packaging, and PHP syntax.

## Executive assessment

The latest GitHub source is syntactically valid on the available PHP 8.3 CLI and has a generally sound security baseline: capability checks are present for the settings page and reset action, the reset action uses a nonce, user-facing output is escaped, and arbitrary URL diagnostics use `wp_safe_remote_head()`. However, the audit found one **high-impact functional bug** and several medium-priority robustness or release-quality issues. No code was changed during this audit.

## Findings

| ID | Severity | Location | Finding | Impact |
|---|---|---|---|---|
| F-01 | High | `devjoynal-downgrade.php:285` | The custom-download checkbox is rendered without a hidden `0` input. When an administrator previously enables the custom URL and later unchecks the box, the browser submits no value for that option; the Settings API therefore may leave the stored option enabled. | The plugin can continue using a custom package URL even though the administrator believes it has been disabled. This is the most important functional defect. |
| F-02 | Medium | Plugin header line 7; `readme.txt` header | The main PHP header says `Requires at least: 5.8`, while `readme.txt` says `Requires at least: 3.0.1`. | WordPress.org and other tooling may display contradictory compatibility information. The lower value should not be advertised unless the code is actually tested against it. |
| F-03 | Medium | `devjoynal-downgrade.php:180-193` | Diagnostics only performs a HEAD request and treats HTTP 200/301/302 as reachable. It does not verify ZIP content type, file size, archive structure, checksum, or signature. Some hosts reject HEAD even though GET works; a non-ZIP 200 response can also appear healthy. | The UI can produce false negatives or false positives. This is a diagnostic accuracy issue, not direct code execution, because the actual package is still handled by WordPress Core. |
| F-04 | Medium | `devjoynal-downgrade.php:206-219` | The filter rewrites only `$updates->updates[0]`. WordPress core update data can contain multiple update objects/channels/locales, and the first entry is not a durable guarantee of the preferred target. | The pin can be bypassed or behave inconsistently when multiple update entries are present. The update selection should explicitly find or construct the intended locale/version entry. |
| F-05 | Medium | `devjoynal-downgrade.php:164-167`, `285-287` | A custom HTTP(S) ZIP URL is intentionally trusted without integrity verification. The readme documents this limitation, but the setting provides no checksum or host allowlist. | A compromised or mistyped URL can supply an untrusted WordPress package. This is a supply-chain risk whenever the optional custom URL is enabled. |
| F-06 | Low | `devjoynal-downgrade.php:30` | `pre_site_option_update_core` is registered, but the implementation is designed for the `site_transient_update_core` object and returns the input unchanged for the network-option filter. | It does not contribute useful behavior and can confuse maintenance. It should be removed unless a deliberate multisite network-option use case is implemented. |
| F-07 | Low | Repository state | GitHub `main` contains both the renamed `devjoynal-downgrade/` implementation and the legacy `downgrade/` implementation. The local checkout also has the old directory marked deleted but those deletions are not committed. | Cloning the repository exposes two plugin entry points and creates avoidable packaging ambiguity. The release ZIP is correctly rooted in `devjoynal-downgrade/`, but the source tree should be cleaned in a follow-up commit. |

## Checks that passed

The latest commit was synchronized successfully from GitHub. `php -l devjoynal-downgrade/devjoynal-downgrade.php` reported **No syntax errors detected**. A search for common high-risk constructs found no `eval()`, `base64_decode()`, `unserialize()`, direct cURL usage, or raw `file_get_contents()` in the main source. The code uses `wp_safe_remote_head()` for arbitrary URL checks; WordPress documents that this function validates the URL and its redirects to reduce SSRF risk [1]. The Settings API form is submitted to `options.php`, which WordPress documents as providing capability checking and nonce-related protections [2]. The `plugins_api_result` callback has the expected three-argument shape (`$res`, `$action`, `$args`) [3].

The `v2.0.3` GitHub release exists and includes `devjoynal-downgrade-2.0.3.zip` and its SHA-256 file. The local ZIP hash matches the repository’s recorded value: `1a642a2ebd46842d68c7f04328329c0962aa2dc1a3557b73bd979c87cd34c583`. The package root is correctly `devjoynal-downgrade/` and contains the renamed main file, readme, translations, screenshots, and author image.

## Recommended remediation order

First, fix F-01 by adding a hidden field before the checkbox:

```php
<input type="hidden" name="wpdg_edit_download_url" value="0" />
<input type="checkbox" name="wpdg_edit_download_url" value="1" <?php checked( $custom_enabled ); ?> />
```

Then add tests for enabling and disabling the custom URL, clearing the target version, invalid version rejection, invalid URL rejection, and reset authorization. Next, make the core-update filter select the correct update object by locale and target version rather than assuming index zero. Improve diagnostics with a short GET/range probe or a clear “HEAD unsupported” fallback, and display that diagnostics are only reachability checks unless content verification is added. For the optional custom URL, the safest production design is a checksum field or an explicit trusted-host allowlist; at minimum, keep the warning prominent and never imply that the archive has been verified.

Finally, remove the legacy `downgrade/` directory from GitHub in a dedicated cleanup commit, update the readme compatibility value to match the PHP header, regenerate the ZIP and SHA-256 file, and rerun the audit before the WordPress.org submission.

## Conclusion

The plugin is not showing an obvious remote-code-execution pattern or PHP syntax failure, but it should **not yet be described as fully bug-free**. F-01 should be fixed before production distribution. F-02 through F-07 are important follow-up items for correctness, maintainability, and release hygiene.
